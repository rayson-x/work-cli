# 微信转发视频本地能力验证（2026-08-30）

## 验证范围

对 8 月 9 日转发会话中的 4 段视频进行真实处理：record 23、30、36、38。验证目标不是比较大模型榜单，而是确认普通办公电脑能否用轻量预处理，把视频压缩成足够让多模态 LLM 理解和回链的证据。

本轮刻意不运行本地 VLM/Omni。电脑只执行 FFmpeg 媒体处理；`faster-whisper base/int8 CPU` 仅作为当前环境不能直接读取本地音轨时的临时转写探针，不作为产品默认依赖。

## 实测成本

| 项目 | 实测结果 |
|---|---:|
| 4 段视频总时长 | 147 秒 |
| 原视频总大小 | 19,523,744 bytes |
| 16 kHz 单声道 48 kbps 音轨 | 885,312 bytes |
| 4 张联系表 | 189,756 bytes |
| 送给多模态 LLM 的首轮派生数据 | 1,075,068 bytes |
| 相对原视频缩减 | 94.49% |
| 4 段音轨提取 | 16.7 秒（顺序执行） |
| STT 首次模型下载/加载 + r23 | 38.45 秒；其中加载开始约 35.1 秒 |
| 模型已缓存后 r30+r36+r38 | 6.76 秒 |
| 带领域提示重跑全部 4 段 | 11.17 秒 |

这些数字说明：首轮没必要上传原始视频，也没必要在办公电脑运行本地视觉大模型。确定性媒体处理可把 19.5 MB 缩为约 1.08 MB，再交给远端多模态模型；遇到疑点时才回取局部高分辨率帧或短视频片段。

## 真实理解结果

### record 23

- 画面对象：灰色针织片、灰色成衣参考、浅蓝配件、纱线色卡。
- 音频事实：供应方比较 24 支与 26 支纱线；24 支织片不够接近样衣的细腻质感，已另试 26 支；26 支现有颜色不完全匹配，色卡中有候选颜色，要求选择支数/颜色方向。
- 可形成的业务结论：这是针对同一产品的“试片结果反馈 + 纱线支数/颜色方案待确认”，不是普通的视频附件。
- 时间证据：约 0–22 秒为支数、粗细和试片说明；约 22–36 秒为色卡候选；约 36–50 秒为 24/26 支选择建议。

### record 30

- 画面对象：米白针织上衣、黑色饰边/纱线、纸样或款式资料、对比样片。
- 音频事实：供应方说明会寄片确认后再起版；当前材料/饰边存在替代方案；画面中的杂点可忽略，需重点确认厚薄和织法，并参考既有爆款厚度。
- 可形成的业务结论：这是另一产品的“替代材料/织法/厚薄方案展示 + 寄片后起版的条件性计划”。它不能与 record 23 合并成一个产品事件。
- 时间证据：约 0–14 秒为寄片后起版与替代方案；约 19–30 秒为杂点和厚薄说明；约 30–54 秒为织法/厚度建议。

### record 36

- 画面对象：灰色针织片、酒红色边料/样片、款式资料。
- 音频事实：当前某一支数/做法过粗过厚，提出另一种支数/材料方案；准备把两个样片钉在色卡上，并连同相关色卡/样衣带过去。
- 可形成的业务结论：这是第三产品的“试片厚度不合适 + 替代方案 + 实物资料交接计划”。
- 时间证据：约 0–9 秒为厚度问题和替代方案；约 9–18 秒为样片、色卡和样衣的交接安排。

### record 38

- 画面对象：浅蓝/白色针织片、蓝白条纹样片、款式资料。
- 音频事实：完全复现样衣颜色较难，提供若干接近颜色；展示两种支数方案，并比较撞色/拼色效果与素色效果。
- 可形成的业务结论：这是第四产品的“颜色难以完全匹配 + 多组纱线/效果候选待选择”。
- 时间证据：约 0–7 秒为颜色匹配问题和候选；约 7–12 秒为两种支数；约 12–18 秒为拼色与素色效果比较。

## 对原有识别流程的直接修正

1. **一条转发会话可以并列打开多个产品槽位。** 这四段视频的主体、材质、颜色和款式资料明显不同；不能把相邻的“这些”“都”“寄过去”简单吸附到最近一个 Style。
2. **视频本身能产生 Event 候选。** 只有当音画共同给出具体对象、发生/反馈/交付/决策内容和时间证据时才放行；“发了一个视频”不是 Event。
3. **STT 不是事实源。** base 模型把“纱线、样衣、织片、支数、起版、半边绒”等词多次误写；即使加入领域提示，专有词改善有限。Agent 必须同时看画面和上下文，必要时回听原音轨。
4. **画面与音轨互补。** 音轨解释“为什么换支数/颜色/厚度”，画面确认说的是哪件产品、哪块样片和哪张色卡。缺任一边都会产生错误款式关联。
5. **款号不是首轮分槽的必要条件。** 首轮可先按稳定的视觉对象槽位分开；后续聊天出现款号、成衣或同一纸样时，再把早期 Event 回挂到对应 Style。

## 推荐默认架构

```text
微信视频
  -> 本地无模型证据处理
     - 媒体哈希、时长、音视频流
     - 场景切分 + 均匀帧兜底 + 相似帧去重
     - 低码率音轨和带 PTS 的候选帧
  -> 远端多模态 LLM
     - 输入聊天窗口、发言人身份、音轨/转写、候选帧
     - 输出产品对象槽位、候选 Event、候选时间段、需要补看的位置
  -> 本地按时间回取原帧/短片段
  -> LLM 二次确认
  -> 保存 Event + Style 关联 + 可播放证据
```

本地可选增强只允许轻量组件：场景检测、相似图去重、OCR，以及 YOLO26n 量级的检测/追踪。YOLO 只能帮助定位衣物、纸张、色卡和对象移动，不能判断款式身份、打样进度或业务结论。若直接采用 Ultralytics YOLO26，还要单独处理其 AGPL-3.0/企业许可问题。

## 建议的媒体证据合同

```json
{
  "media_id": "sha256:...",
  "interval": {"start": 22.18, "end": 35.90},
  "audio": {
    "path": "derived/audio.mp3",
    "transcript": "供应方展示色卡中的候选颜色",
    "transcript_is_interpretation": true
  },
  "frames": [
    {"pts": 24.80, "path": "frames/000024800.jpg"},
    {"pts": 32.10, "path": "frames/000032100.jpg"}
  ],
  "claim": "已提供与目标样衣接近的颜色候选，等待选择",
  "style_slot": "forward-0809-object-a",
  "confidence": "needs-review"
}
```

转写文本要显式标记为模型解释，原音轨时间段与原帧才是可核查证据。

## 结论

这批真实视频已经证明：轻量本地媒体处理 + 远端多模态 LLM 的路线可行，而且比“纯文本聊天抽取”多恢复了关键的材料、支数、颜色、厚薄、试片和起版条件。第一版不应要求办公电脑运行本地 VLM；本地模型最多作为可选 STT 或 YOLO 量级的索引增强，默认流程仍应允许完全不加载模型。
