# 视频证据与业务理解

本文件规定 Agent 如何从视频恢复可核查的产品工作事实。目标是理解具体产品发生了什么，不是生成整段视频摘要，也不要求办公电脑运行本地视觉大模型。

## 1. 输入边界与证据身份

- 只有 wechat-cli 返回了可读取本地资源路径，才分析视频内容；`source unavailable` 只登记原消息存在，不推测音画。
- 原视频消息及其不可变来源坐标是 Evidence。音频转写、OCR、对象标签、关键帧说明和模型结论都是派生解释；保存时必须能回到原视频的时间段与画面。
- 同一视频可支持多个 Event；同一 Event 也可由视频、前后文字、回复链、图片和后续确认共同支持。
- 视频缩略图、首帧或单张联系表不能替代整段视频。它们只用于首轮定位。

## 2. 默认能力预算

默认本地处理只做确定性、低资源工作：媒体探测、抽音轨、场景切分、稀疏取帧、相似帧去重、按时间回取原帧和缓存。允许使用 OCR、场景检测或 YOLO26n 量级的可选检测／追踪帮助定位，但这些组件不能输出业务事实。

不要把本地 VLM、Omni 或大参数 STT 设为准入条件。优先把压缩音轨、聊天上下文和少量带时间戳候选帧交给当前可用的远端多模态 LLM。当前模型能直接读取短视频／音轨时可以直接使用，但仍要保存可寻址的时间证据；不能直接读取音频时，可调用可用的远端转写，或将轻量本地 STT 作为可选降级。STT 错词不阻断视频理解，也不得单独决定款号、支数、材料或业务状态。

控制成本的顺序是：

1. 复用 `content_hash` 缓存，已处理视频不重复解码或上传；
2. 首轮只发送低码率单声道音轨、场景代表帧和均匀帧兜底；
3. 让模型先返回候选业务区间、对象槽和存疑点；
4. 只对存疑区间回取原分辨率帧、局部音轨或短视频；
5. 款号/OCR/细节决定 Style 身份时才读取原分辨率。

## 3. 两遍音画理解

### 第一遍：恢复视频内的对象与候选区间

结合视频前后的聊天、回复对象、发言人身份和当前尚未关闭的产品槽，检查：

- 视频展示的是哪几个可见对象；一段视频也可能包含多个 work target、reference 或 alternative；
- 每个对象在画面中的稳定特征、出现区间和业务角色；
- 音轨说到的支数、材质、颜色、厚薄、工艺、版本、问题、动作与时间；
- 语音中的“这个/这几个/这块/它”在对应时间点指向哪个画面对象；
- 是否出现试片、对比、修改演示、交接、包装、物流、成衣结果或版单；
- 哪些区间可能产生事实、反馈、问题、计划或承诺。

连续发送多个视频时，先把每段视频作为独立对象槽候选，再用版单、回复链、明确回指和视觉连续性合并。发送顺序、同一发言人、相邻时间或同色不能单独合并。供应方一次展示四件产品时，应保留四个槽和共同批次作用域；批次不是 Style。

### 第二遍：针对候选结论回取证据

对每个候选结论回到对应时间窗，至少核对：

- 语音原意是否被转写错词改变；
- 画面是否确实展示该对象、材料、样片、色卡或状态；
- 这是当前 work target、参考样还是候选方案；
- 说话人是在陈述已发生事实、给反馈、提问、提出计划还是作出承诺；
- 前后文字是否回答、否定、限制或把结论扩展到整个批次；
- 该结论能否关联至少一个已有／候选 Style。

如果音轨与画面冲突，保留冲突 Evidence，不挑一个顺眼的解释。仍无法确认对象时，视频只进入上下文和覆盖账本，不创建 Event。

## 4. 视频 Event 准入

视频候选仍必须通过主规则的四项正向准入。以下情况经常可以形成 Event：

- 展示已经完成的试片并反馈其与样衣的差异；
- 比较多个材料、支数、颜色或工艺方案并提出当前对象的选择问题；
- 明确指出当前样衣/样片的问题或修改要求；
- 展示已完成、已寄出、已收到或正在加工的具体结果，并有足够音画/文字依据；
- 对具体对象承诺寄片、起版、修改或交付，并说明条件或时间。

以下内容不得单独形成 Event：

- “发送了一段视频”；
- 只有衣物画面，但不知道是参考物、当前样还是其他款；
- 只有 STT 识别出的词，画面、聊天与身份均不能支持；
- 只展示材料属性，没有对具体产品形成变化、决定、反馈或下一步；
- 用画面外观自行推断“已确认/已完成/已交付”。

一段视频同时包含“已试出某方案”和“之后寄片再起版”时，前者是 `fact`，后者是 `commitment` 或 `plan`，必须拆成可分别验证的 Event。视频中连续解释同一个问题的原因、比较和建议，最终只形成一个业务结论时合成一个 Event，并把各时间段作为共同 Evidence 解释。

## 5. Style 归属与多产品批次

- 正式款号未知时，使用视频中的稳定产品对象槽连接 Event，并创建或复用 candidate Style；不能因为没有款号丢弃事件。
- 视频中的纸样、版单、吊牌和款号是 Style 锚点；使用前在原分辨率复核字符，并判断它属于客户/设计师编号、工厂编号还是其他命名空间。
- 不同视频展示不同衣物、材料组合或版单时保留独立槽；后续证据证明同款后再合并，不提前压成一个 Style。
- 后续款号、成衣、结果图或明确回指确认早期无编号视频时，沿对象槽和证据链回补早期 Event；款号第一次可读时间不是 Style 的开始时间。
- 视频只展示 reference 或 alternative 时，它可以支持 work target 的决定，但不得因特写对象更清晰就把 Event 挂到参考物。

## 6. 可核查的视频证据卡

分析态为每段使用过的视频保留紧凑证据卡：

```json
{
  "source_coordinate": "outer_message_id + forward_path + record_index",
  "media_hash": "sha256:...",
  "duration_seconds": 51.4,
  "speaker_identity": "source-identity-id",
  "object_slots": [
    {"slot": "object-a", "role": "work_target", "visual_basis": "..."}
  ],
  "claims": [
    {
      "interval": {"start": 22.18, "end": 35.90},
      "transcript_interpretation": "...",
      "frame_pts": [24.80, 32.10],
      "business_conclusion": "...",
      "expression_mode": "feedback",
      "style_slot": "object-a",
      "uncertainty": "..."
    }
  ]
}
```

写入 Workline 时：

- 原视频消息使用 `content_type=video`；`raw_locator` 保存来源媒体坐标、hash、时长和派生证据清单；
- `image` 可以上传带时间标注的联系表或最能核查结论的代表帧，但不得假装它是原始图片消息；
- `excerpt` 只放简短的音画解释并明确其为解释，不逐字伪造转写；
- EventEvidenceLink 的 `interpretation` 必须说明此视频的哪个时间段、语音和画面支持 Event 的哪一部分；
- Event 摘要写业务发生，不写“视频显示/某人说了一段视频”。

## 7. 完成检查

范围中每个可读取视频都必须具有下列处置之一：支持 Event、支持 Style 锚点、仅作对象/身份/流程上下文、与业务无关并有原因。不能再使用“视频类型未支持”跳过可读取资源。

最终逐项检查：

- 是否只转写而没有看画面，或只看联系表没有检查音轨；
- 是否遗漏无语音但画面中出现的版单、款号、状态变化；
- 是否把一轮多产品展示压成一个对象；
- 是否把同一视频内的事实、反馈和承诺混成一个 Event；
- 每个视频支持的 Event 是否有明确 Style 归属和可回查时间段；
- STT/OCR 存疑是否被诚实保留，原音轨与原帧是否仍可核查。
