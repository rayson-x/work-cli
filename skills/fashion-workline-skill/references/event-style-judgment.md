# Workline 判断规则

本文件是 Agent 的语义判断规则。它不定义业务代码，不允许绕过 Workline CLI 写飞书。

## 1. 确定聊天范围

### 有明确范围

用户或保存配置给出微信账号、联系人/群聊和时间范围时，取这些范围的并集，严格限制读取到的会话与时间。可以同时指定多个单聊、群聊、多个账号和多个时间段；Event 的行动者不必是当前读取账号。

### 只有人员、款式或关键词

先用当前环境提供的授权微信读取能力解析联系人、群聊和当前微信账号的稳定 ID，再用微信 ID、群成员、近期消息和款号/款名/别名消歧。形成候选范围后只处理唯一解析的会话；交互运行仍无法唯一确定时，请用户选择。无人等待时跳过歧义项，并说明跳过了什么。

用户指定“最新转发”“最后一条转发”等相对范围时，先在已解析会话内枚举符合类型的外层消息，按外层消息的 `source_time` 和会话顺序选择最新一条，再读取其内部记录。不得按转发内容中的最晚时间、先前记住的消息 ID 或内层记录顺序替代这个判断。结果中同时说明外层消息时间和内层内容覆盖时间。

### 增量与历史

按 `wechat_owner_id + conversation_id` 记录上次成功读取位置；下次从 checkpoint 向前保留少量上下文重叠，重叠消息依靠 Evidence source key 去重。用户明确要求更早历史时，不能被 checkpoint 截断。历史补录只能增加或修正解释，不能改写当时的发言人、来源时间或原始内容。

### 输入投影与覆盖账本

在语义判断前为用户指定范围建立有序输入清单。合并转发使用内部 `record_index`；普通聊天使用稳定消息顺序。语义输入只保留判断所需的来源坐标、时间、sender、正文、回复/转发关系和资源索引；完整 XML、CDN 参数、头像 URL、重复 raw content 等只留在本地原始 artifact，不进入模型上下文。

范围较长时分成适合当前上下文的连续片段并保留重叠，从首条推进到末条，禁止抽样、只找款号或只处理最新片段。覆盖账本随片段推进增量填写，使用紧凑的 `source coordinate / cluster / disposition / linked IDs or reason`，不逐条复述原文，也不要求先写成长篇报告。

每条记录在结束前都要进入一个消息簇，并具有至少一种可审计处置：

- 支持 Event；
- 建立或支持 Style 锚点；
- 仅作为回复、对象、身份或流程上下文；
- 与业务无关，并写明简短原因；
- 媒体类型尚未支持；
- 消息存在但资源为 `source unavailable`。

处置不是把所有消息都写成 Event；它证明 Agent 实际检查过完整范围。一个记录可同时是 Style 锚点和 Event Evidence。当前片段的来源坐标确定后即可保存 Evidence；当前片段完成局部覆盖复核后即可写入其 Event/Style 判断，不等待全范围账本完成。完成一段后记录首末坐标、消息簇和未决对象；下一段先读取重叠和未决对象再继续。结束前核对首末坐标连续、每条记录有处置、每个未决对象有去向。完整账本只决定能否宣称整轮完成，不能用“只写强证据”代替覆盖。

## 2. 来源 envelope、身份与“我”

每条进入判断的消息都要能定位到以下字段：`wechat_owner_id`、`conversation_id`、`conversation_type`、`message_id`、`source_time`、sender 微信 ID、reply target、forward path、图片资源和相邻上下文坐标。

- 本地“我”先映射为当前微信账号 ID，再查询 `SourceIdentities` 和 `People`；不能把“我”直接当作真实姓名。
- 群聊必须使用消息的真实 sender 微信 ID；群名不能代替人员。
- 转发者只记录为转发来源；转发内部条目的原作者才是原始发言人。转发路径写入 Evidence 的 `forward_path`，避免与原消息混淆。
- 转发内部条目没有独立 `message_id` 时，不得伪造消息 ID。稳定来源坐标使用 `outer_message_id + forward_path + record_index`；若条目另带 `messageuuid`，同时保存为辅助来源标识。
- 转发内部若提供 `hashusername` 等来源生成的匿名发言人键，它虽然不是公开微信号，但可以建立可回查的 SourceIdentity。把完整、命名空间化的键写入 `source_identity_key`，并设置 `identity_kind=forward_hash` 与能够限定该键语境的 `identity_scope`；`wechat_id` 必须留空。不能截断 hash，也不能仅凭显示名生成身份键，更不能把匿名来源键伪装成真实微信 ID。
- 图片和视频消息沿用消息的 sender、conversation、message ID 和 source key；媒体本身可以支持视觉／音画判断，但不能因为视觉相似、STT 词面或同一发送人自动认款。
- 图片消息存在但媒体文件未成功读取时，只能记录“存在图片但视觉内容未验证”，不得依据 `[图片]` 占位符推断款式、版本或修改内容。
- 视频消息存在但媒体文件未成功读取时，只能记录“存在视频但音画内容未验证”，不得依据缩略图、占位符或后续模糊应答补写视频内容。可读取视频必须按 [video-evidence.md](video-evidence.md) 完成音画联合检查。
- 回复优先通过 reply target 连接被回复消息，不能只凭相邻时间猜对象。
- 无法解析原作者时使用 unresolved SourceIdentity；不捏造 Person。能判断业务行动但不能确认真实人员时，Event 必须保留该 SourceIdentity，真实 Person 保持空/未解析，不能把发言来源一起丢掉。
- `SourceIdentity` 是可持续回查的微信来源身份；`Person` 是真实人员；`RoleClaim` 是 Person 或 SourceIdentity 在指定全局、会话、Style 或时间范围内的职能。不要用显示名直接替代三者。Person 未解析时，场景角色先挂 SourceIdentity；以后映射 Person 不删除原身份级 RoleClaim，也不自动升级成人员全局角色。
- 转发内部昵称与已知联系人的 `alias`、`nick_name` 或历史显示名一致时，可以建立 `inferred` 身份映射，但必须保留内部原始 sender 字符串，不能把推断映射写成已确认身份。

同一转发内每个具有不同稳定匿名键的原作者都应分别建立 SourceIdentity，即使暂时无法映射 Person。已有联系人别名与匿名键显示名一致时，可以把该 SourceIdentity 以 `inferred` 关联到已有 Person；没有足够映射依据时保持 `unresolved`，不创建 Person，但可以依据多条发言和相邻协作关系创建限定范围的 SourceIdentity RoleClaim。只在正文中被提及、没有任何稳定来源身份键的人名或组织，不因此创建 SourceIdentity。

身份写入前，只有稳定 ID 和必要依据才可建立 `identity.upsert`；映射仅有推断证据时标为 `inferred`，用户或明确资料确认后才为 `confirmed`。角色必须有 supporting Evidence，区分发言所体现的职能、组织归属与真实姓名；变化按范围和有效时间记录，不用当前角色重写历史 Event。

### 条件式身份复核

先查询已有 SourceIdentity／Person／RoleClaim。相关发言人已有稳定身份、没有同名冲突，并且现有身份信息足以解释本轮对话时，直接进入 Event 判断，不重复读取和分析。

仅在以下情况触发第二遍身份 review：发言人 unresolved／inferred；同一显示名可能对应多人；转发内外身份映射不清；或某人的职能会实质改变一句话中的实际行动者、责任对象或业务含义。此时先写入并回读有稳定依据的新增身份／职能，再只重新分析受影响的消息簇、Event 和工作线，不重跑无关范围。

复核必须形成 review diff，说明 actors、`expression_mode`、摘要、工作线或 Style 关联是否变化及证据。角色上下文是解释线索，不是业务事实证据；不得因为第一遍从某句话推断某人是“跟单”，第二遍再用“他是跟单”反向证明同一句话描述的动作已经发生。复核后仍无法确认时保留 unresolved／inferred，不以“复核过”作为升级为 confirmed 的理由，也不无限循环。

### 图片理解与图像链

图片首先是 Evidence，不是 Style，也不天然构成 Event。媒体成功读取后，为每张图片记录一份可核查的视觉证据卡；只描述画面中实际可见的信息：

- 媒体是否成功读取，以及画面是否足以判断；
- 对象类别：参考资料、设计表达、色卡/材料、试片、过程样、当前样衣、局部细节、物流或文字截图、未知；
- 可见特征：颜色范围、纹理/条纹、轮廓、领口、门襟、口袋、扣件、辅料、工艺细节和明显问题；
- 它与哪条文字、回复目标或前后图片发生比较，比较依据是什么；
- 图像关系是明确延续、可能延续、明确不兼容还是未知；
- 任何 OCR 结果及其可读性；不可辨认的字样、款号和标签不得补写。

一张图片可能同时包含多件款式、参考样和当前样、多个试片或多个钮扣方案。先把可见对象拆开并记录各自特征与位置，再判断文字指向哪个对象；不得把整张图片当作单一 Style。图片中的设计单、款号栏、工厂款号、吊牌或手写标识是 Style 锚点，清晰可读时优先使用原文；只读到部分字符时保存候选读数与可见范围，不用视觉描述替代可读编号。

同图多对象除了位置与特征，还必须标注它在当前业务动作中的角色：`work_target`（正在设计/生产的对象）、`reference`（用于比对或决定做法的参考对象）、`alternative`（候选方案）或 `unknown`。连续发送多组图片/视频时，为每组建立独立对象槽，并保留共同批次；媒体顺序只定义候选邻接，不证明同款。当对话表示“等待/收到参考样衣，再决定当前款的钮扣、工艺或尺寸”时，参考样衣图片可以作为 supporting Evidence，但由此形成的决定、反馈或承诺应关联 `work_target`，不能因为特写拍的是参考对象就把 Event 挂到参考对象或另一条 Style。

### 多产品批次与作用域

供应方可以在一轮对话中连续交付多件产品的信息。先识别批次边界，再把其中每组设计图、实物、试片、视频和版单拆为独立产品对象槽。批次只是消息作用域，不创建为 Style。

- “这些/这一批/都/一起”默认指向当前尚未关闭的对象批次，而不是只指向距离最近的单张图片；后续连续补发的对象资料在没有话题切换时可以补入同一批次。
- 批次成员由对象槽决定。资源缺失但能确认存在独立第四组资料时，保留未知对象槽和原 Evidence，不能把它吸收到前三款，也不能虚构视觉特征。
- 一个要求、决定或承诺确实同时作用于多个成员时，只创建一个 Event，并通过多条 EventStyleLink 关联所有已确认成员；每条 Link 的 basis 说明该 Style 如何属于该批次。
- 后续某款出现单独结果、偏差、反馈或取消时，从共享 Event 分叉，只关联该款；不得把单款结果广播到整个批次。
- 后续清晰款号或结果图确认某个对象槽时，只回填该槽及共享 Event 的对应 Style Link，不影响其他成员。

视频中的语音可以一次概括多个对象，画面也可能依次扫过多件产品。先依据视频时间段、画面切换和指代表达把结论落到对象槽，再判断它是单款还是批次共享；不能把整段视频只挂到第一件或最后一件产品，也不能把一句“这些都”机械复制成多个同义 Event。

款号 OCR 一旦用于创建、确认、合并或重命名 Style，必须在原分辨率下再次核对完整字符，并与同图版单标题、相邻文字或已有别名交叉验证。单个数字/字母仍可能有两种读法时，保留候选读数和待复核状态，不选择视觉上更顺眼的一个写成 confirmed。

先通过回复目标、图片所在消息、明确回指和紧邻的说明文字判断图片在对话中的用途，再让视觉特征参与工作线判断。仅有相邻位置、相似外观、相同颜色或相同发送人时，最多形成候选关系。

多张图片若共同展示同一对象、不同角度或同一处问题，应作为一个证据簇，不按图片数量制造 Event。图片用于证明或解释附近的反馈、交付、确认或阻塞时，附到该 Event；只有“提供这份视觉资料”本身改变了业务进展且无法归入其他 Event 时，才生成独立 Event。

不得只凭成品外观推断“已完成”“已确认”或“已交付”。参考图、原版图、网络图与当前生产实物必须分开；没有文字锚点时，不把它们识别为同一 Style 或不同版本。可以依据明确回指建立“参考资料 → 试片/过程样 → 样衣 → 修改后样”的图像链；证据不充分时关系保持 `proposed`。

媒体未成功读取时，只保留图片占位 Evidence，不生成视觉特征、OCR、版本关系、Style 关联或完成状态。后续取得媒体后再补充解释，不改写原始 Evidence。

## 3. 上下文与工作线

先按强锚点连接，再用辅助锚点补充：

- 强锚点：明确款号/款名/双方已知别名；对设计图、试片或样衣图片的直接回复；同一回复链或转发内部连续对话；“这个款/上一版/那件/同一件”等明确回指；已有 EventRelation 或 EventStyleLink。
- 辅助锚点：供应商、参与人员/职能、面料、颜色、版型、部件、工艺、时间连续性和图片演变特征。

出现明确“另一个款/新款/不是这个”、不兼容对象描述、并行推进的不同图片或独立回复链时，分成不同工作线。不同编号只有在确认属于同一签发方、同一编号种类且不存在改号/版本关系时，才是强拆分信号；设计师编号与工厂内部编号不同本身不是反向证据。只有同一群、同一供应商、同一参与人或时间接近时，不得合并工作线。

### Event 对象锚点与 Style 双向重建

先从证据簇确认具体工作对象，再判断该对象是否产生 Event；Style 是同一对象的 Event 与视觉/款号锚点逐渐聚合形成的持续身份。对象在分析态至少记录稳定锚点、对象角色和依据；正式款号未知不影响 Event 判断，但对象本身未知时不得创建 Event。

新 Event 或 Style 锚点出现后进行双向重建：

1. 向前回溯到上一个明确不同对象、独立回复链或范围起点，检查先前的试片、材料、寄送和问答是否属于同一对象；
2. 向后追踪明确回指、同款版单/标签、相容的图像演变和后续决策，直到出现强反向证据或工作线切换；
3. 后段出现款号、版单或清晰图片时，重新检查受影响的早期 Event 与 candidate Style，而不是从锚点出现时才开始 Timeline；
4. 共享动作的成员明确时，一个 Event 可关联多个 Style；成员未知时保留为 Evidence／上下文，不创建无 Style Event，也不把 batch 伪装成 Style。

每个 Style 记录首次明确/候选出现、最后一次出现、使用的强锚点、主要反向证据和仍未解释的间隔。空 Timeline Style 必须经过上述回溯并说明为什么相关消息都不足以形成 Event；不能仅因创建来源是一张图片就停止。

## 4. Event 判定、表达性质与消息粒度

Event 表示具体工作对象的一次可独立追踪业务发生，不表示一条消息，也不等同“聊天中的重要内容”。先把同一回复链、对象、问题、版本和时间窗口内的文字与图片组成证据簇；在分析态为对象记录稳定锚点与依据，再判断其中包含几次业务发生。Style 可以随后派生，但对象锚点不能缺失。

### 正向准入：四项必须全部满足

1. **对象可追踪**：能指出具体款式、无款号但持续存在的产品对象、试片/样衣工作目标，或成员明确的多款批次；材料、参考物、季度或泛化流程本身不是产品对象。
2. **业务发生有变化**：状态得到确认或改变；形成影响行动的决定、规格确认、门槛或约束；产生有承担者的计划/承诺；提出有效反馈/修改要求；暴露本对象的阻塞/依赖；发生交付/接收；或形成未关闭的可执行事项。
3. **Evidence 闭合结论**：能够回答谁行动或表达、对哪个对象、发生/决定/要求了什么、表达性质、时间依据及哪些 Evidence 支持。人员可 unresolved，款号可未知，但对象和变化不能同时含糊。
4. **可继续追踪**：该结论以后能够被完成、确认、修改、取消、反驳、延误或关联；移除后会丢失一项产品工作状态、要求、责任或下一步。

### 硬性否决：命中任一项不单独建 Event

- 泛化知识、行业经验、常规职责、季度/季节策略或成员未知的批次状态；
- 问候、表情、情绪、修辞性问题、普通确认或无新含义的“收到/好的/明白”；
- 单独图片、视频、地址、快递卡片、人员@或只提及材料/属性但没有业务变化；
- 已被回答的问题、对已有结论的重复表达或只补充原因/细节的消息；
- 无法指向具体工作对象的动作描述；
- 媒体未读取却依赖其不可见内容才能成立的判断；
- 假设性讨论尚未形成决定、责任、约束或可执行事项。

硬性否决只拦截误报，不能替代四项正向准入。不得因为未命中黑名单就创建 Event。

如果移除候选不会丢失任何可独立确认、反驳、完成、延误或关联的业务事实，它通常只是另一 Event 的 Evidence，而不是 Event。

`expression_mode` 严格按表达内容保存：

| mode | 判断 | 不得混写 |
|---|---|---|
| `fact` | 证据表明行动或状态已经发生，例如“已寄出/今天改完” | 不能把未来安排写成 fact |
| `plan` | 未来安排或意图，尚未形成对外承诺，例如“计划下周打版” | 不能当作已执行 |
| `commitment` | 某人对未来结果、时间或动作作出承诺，例如“明天寄给你” | 不能写成已寄出 |
| `question` | 尚未得到解决且形成待处理事项的询问、催问、请求确认或请求进度 | 不能自动推断对方已完成；已有明确回答时优先归入回答形成的结论 Event |
| `feedback` | 对样衣、设计、材料、工艺或结果给出的评价/修改意见 | 不能把意见写成修改已完成 |
| `reported` | 当前发言人转述别人或外部发生的事项 | 发言人是报告者，行动者按转述内容解析，未知时不捏造 |

### 应拆成多个 Event

- 同一消息同时包含已发生事实和未来承诺/计划；
- 不同人员分别承担不同动作；
- 涉及不同 Style 或不同版本；
- 一个动作已完成，另一个只是要求、询问或反馈；
- 两个动作可被后续消息分别确认、否定或修改。

拆分后同一 Evidence 可以关联多个 Event；不要通过给摘要加序号来制造唯一性。

### 可以合成一个 Event

连续消息围绕同一对象和问题共同产生一个结论、决定或状态变化时，合成一个 Event，即使消息由不同人发出或包含问题、回答和确认。问题、回答、理由、无新含义的确认以及配图共同作为 Evidence；Event 的 `expression_mode` 取最终业务发生的性质，不按每句话分别建 Event。

连续短消息由同一行动者补齐宾语、时间、材料、原因或图片说明时，也合成一个 Event。后续消息只是重复进度、改写说法或补充证据时，附到已有 Event；只有引入新的状态、承担者、对象、表达性质或可独立追踪结果时才拆出新 Event。

### 不单独形成 Event

问候、表情、无新信息的应答、普通确认、无法结合上下文解释业务含义的孤立图片，以及对已有 Event 的逐字重复转述不单独新增 Event。它们应登记为 Evidence，并附到相关 Event；若引入新的业务含义，则拆出新的 Event。“收到”只有在明确确认样品、资料或货物完成交接时，才可表示独立的接收 Event。

### 粒度归一

生成候选后必须进行第二遍归一，而不是把首轮消息切分直接写入：

1. 将已经得到回答的问答链收敛为回答所确认的结论、决定或状态；仍未解决并形成待处理事项的问题才保留 `question` Event。
2. 将表情、普通确认、理由、图片和重复表述附到它们所支持的 Event。
3. 将同一消息中可分别确认、延期、完成或否定的结果拆开；事实、计划、承诺和反馈不得为省事而混写。
4. 将不同会话或不同发言人对同一次业务发生的记录合并为多 Evidence 的一个候选；证据不足时保持候选关系，不强行合并。
5. 重新检查每个候选：它是否代表业务变化，是否可以独立追踪，摘要是否描述发生了什么而不是谁说了哪句话。

供应商周期、常规职责、固定工艺限制等长期背景只有在本次对话中对一个具体工作对象形成新的决定、阻塞或适用约束时才建 Event；否则作为解释上下文使用。产品规格问答只有在明确解决当前对象的设计/生产问题时才形成规格确认 Event；孤立属性只作为 Style/Evidence 信息。

### 实际时间

- 原文明确发生时间，用该时间，`time_basis=explicit`；
- “刚寄出、昨天改完、上周收到”等相对时间可由消息时间推断，用推定出的实际时间，`time_basis=inferred`；
- 只有消息表达时间、没有实际发生时间时，使用消息时间，`time_basis=message_time`；
- 未知时 `occurred_at` 留空，不用创建时间补齐；
- “明天寄/下周确认”仍是 `plan` 或 `commitment`，发生时间可以记录预期时间但不得改写成事实；
- 若多条 Evidence 对实际时间冲突，保留冲突证据，选择有较强依据的时间并在关系或解释中说明，不覆盖原始 `source_time`。

### 行动者与表达者

Event 的 `actors` 是实际行动者/表达者，不默认填当前微信账号。群聊中“让小王寄样”时，表达者是发言人，预定执行者是小王；若只能确认表达者，行动者未确认则保持空或仅记录可确认的人。

EventEvidenceLink 的 `support_type` 描述 Evidence 对 Event 结论的作用，不描述媒体格式：直接陈述用 `direct`，补充对象/原因/视觉细节用 `supporting`，后续确认用 `confirming`，冲突证据用 `contradicting`，转述外部事项用 `reported`。图片不能因此自创 `visual` 类型；只作为语境且不支持该 Event 的消息不建立关系。

## 5. Event 查重、关系、合并与拆分

先用 `+query` 取同一 Evidence 已支持的全部 Event，以及其他可能描述同一次业务发生的 Event。Agent 结合 Evidence、主体、行动性质、对象、实际时间和前后关系判断：

- 已有规范 Event 覆盖候选含义：复用它，使用 `event.attach_evidence`，不要新建；
- 同一业务发生但来自不同证据：保留一个 Event，附加多份 Evidence；
- 明确是不同催样、复版、寄出或不同版本：保留不同 Event；
- 证据不足以确认相同：保留两个 Event，并用 `event.relate` 建立关系，关系状态为 `proposed`，不要自动合并。

只有在业务上确认是同一次发生时才 `event.merge`。合并时选择 winner，汇集 Evidence、Style 关联和关系，旧 Event 保留 `canonical_event_id`。一个 Event 错误容纳多个具有独立性质、时间、对象或后续验证的发生时才 `event.split`；拆分后的多个 Event 可以继续共用原 Evidence。合并不等于 Style 合并。

## 6. Style 判定与关联状态

Style 是持续设计、修改和确认的同一个产品设计对象，不等于一张图片或一个 Event。建立候选前必须查询已有正式/候选 Style。

### 强同款依据

相同来源范围与编号种类下的明确款号；同一版单同时出现客户/设计师编号与工厂编号；明确“这个款/同一款/上一版/复这个版”；对同一设计稿、试片或样衣图片链的连续回复；已确认标识映射；已有工作线明确延续。强依据足够且没有反向证据时，可以 `event_style.set` 为 `confirmed`。

### 辅助依据与反向证据

视觉相似、同一供应商、时间接近、同面料/颜色/工艺、同一参与人只能作为辅助依据。不同来源范围的编号不等也只是待解释信号；明确“另一个款/新款/不是这个”、同一编号命名空间内的两个独立编号、不兼容设计描述、两条独立回复链并行推进时，才构成反向证据。辅助依据只能形成 proposed 关系，不能单独确认或拆分。

### 同款多编号

Style 使用不可变业务 ID 表示持续产品对象。设计师款号、客户款号、工厂内部号、内部追踪号和 OCR 候选分别作为结构化 StyleIdentifier 保存，至少记录编号值、编号种类、签发方或范围、Supporting Evidence 与状态。`style_code` 只用于主展示，不参与全局唯一性判断；普通称呼才进入 aliases。

- 编号匹配的有效键是 `issuer_or_scope + identifier_kind + normalized_value`，不是裸字符串。
- 同一版单或同一对象链明确出现两个编号时，为一个 Style 增加两个标识；不得创建两个 Style。
- 后段编号或清晰版单确认前段无编号对象时，向前回溯图片、回复、决定与执行结果，并合并原 candidate Style。
- OCR 不确定时保存 `candidate_ocr/inferred`，不得据此确认、拆款或合款。
- Style merge 依赖对象共指证据；编号相似、编号不同、视觉相似都不能单独决定。

### Event-first 的 Style 派生与关联

1. 从 Event 出发时用 `+query` 的 `query=event` 取其 Style、Evidence 和关系；需要按款号、款名、别名或已有 Event 反查候选 Style 时使用 `query=style`。`query=context` 只用于从指定 Evidence 范围扩展上下文，不接受 `event_id/style_id` 作为通用入口。
2. 强依据指向已有 Style：建立 `confirmed` Link。
3. 只有辅助同款依据，但具体产品对象明确：建立或复用 candidate Style，并以 `proposed` Link 关联；不能为了填满 Timeline 猜到某个 confirmed Style。
4. Event 明确证明一个新的持续产品对象开始，且已有 Style 候选都不覆盖时，从 `created_from_event_id` 创建 candidate Style；清晰款号、版单、标签或已确认别名足够时才创建/升级为 confirmed。清晰对象图片在尚无 Event 时可从 `created_from_evidence_id` 建 candidate Style。共享 Event 涉及多个产品时，应为每个对象槽分别复用/创建 Style，再由同一 Event 关联，不创建“批次款式”。
5. 语义上先判断 Event，再派生 Style；工程写入时 Event 与由它派生的 candidate Style 应处于同一 operation，完成后不得留下无 Style active Event。
6. 后续新证据可 `event_style.set` 关联、解除或重新挂载，并通过 Style merge 把临时对象身份并入正式款号；材料、reference、alternative 或成员未知 batch 不能为了消除空关联而建成 Style。

Style 的展示名称优先使用已确认的主展示编号、款名和别名，但必须保留其他来源编号及其标签。只有视觉特征时可以使用便于检索的临时描述，但必须显式标为“系统暂命名/待确认”，不能把它显示成用户确认的款名。图片中同时出现多个对象时，除非文字或版单明确把它们定义为同一 Style 的版本，否则不合成一个 Style。

一个共享寄出/确认动作可关联多个 Style。解除关联使用状态变更/重新挂载，不删除 Event 或 Evidence。

### Style 合并

只有多份证据共同证明两个 Style 是同一持续设计对象时才 `style.merge`；视觉相似、供应商相同或时间接近不够。Style merge 不自动合并全部 Event：迁移关联后仍按 Event 证据逐一判断，旧 Style 保留 canonical 指向。中断后根据 CLI 返回的 operation 状态继续，不另起不可追踪的替代操作。

## 7. 最终检查

对每个创建/修改过的 Style 执行 `workline +style-events --style-id <id>`，核对当前有效 Event、`occurred_at` 与 `time_basis`、确认/候选/失效关联、分支和 canonical 指向。Event Candidate 可以在分析态等待对象判断；完成写入后的 active Event 必须具有至少一个 proposed/confirmed Style 关系，否则把它降级为 Evidence／上下文。

再把回读结果与覆盖账本逐项对照：

- 每个 Style 是否从首次锚点而不是首次被写入的 Event 开始重建；
- 每个空 Timeline Style 是否完成双向回溯并有理由；
- 每个 active Event 是否通过四项正向准入且未命中硬性否决，是否具有至少一个 proposed/confirmed Style 关系；
- 同图多对象和不兼容图片是否被错误合并；
- 同图中的 work target、reference 和 alternative 是否区分，Event 是否错误挂到了被拍摄特写的参考对象；
- 决定 Style 身份的手写/OCR 款号是否经过原分辨率二次核对，是否把单字符存疑误写成 confirmed；
- 每个 EventEvidenceLink 是否有 `support_type` 和说明该 Evidence 支持结论哪一部分的 `interpretation`；
- 每个 proposed/confirmed EventStyleLink 是否有基于款号、回复、对象或图像链的 `basis`，且没有把时间接近当作唯一依据；
- 每个 Event 的来源发言身份是否可回查；Person unresolved 时是否仍保存 SourceIdentity 与有证据的场景职能；
- 同款多编号是否保留签发方/范围和 Evidence，是否因裸字符串不同误拆 Style；后置编号是否回补到对象首次沟通而非编号首次可读时间；
- 多产品会话是否完整识别对象槽；“这些”等批次作用域是否错误收窄到最近图片，或把单款后续结果错误广播到整个批次；
- 每段可读取视频是否同时检查音轨与画面，是否把 STT／关键帧解释误当原始 Evidence，是否保留可回查时间段与代表帧；
- 指定范围的首末记录、分段边界和所有 source unavailable／未支持媒体是否都在账本中。

任一项未满足时，结果只能标为未完成，不能以“已恢复至少一条工作线”代替整段范围验收。
